## 发现清单

### 🟠-1 fix_short_records.py 硬编码 SHORT 列表不完整：9 条短记录仍是旧管线产物（未修复）

- **位置**：`scripts/fix_short_records.py` 第 32–58 行（`SHORT` 硬编码列表）；根因在列表覆盖不全。
- **证据（实测）**：
  1. `SHORT` 列表实为 **45 条**（train 37 / val 5 / test 3，其中 cpsc 仅 `A0798` 1 条，其余 44 条 georgia），与 docstring「49 条短记录」不符。
  2. 全盘扫描 37749 个 npy（`np.all(x==0, axis=0)` 逐列判零）得到 45 条「已正确零填充」记录，恰好等于 `SHORT` 列表；但按 manifest `duration_original < 10s` 统计共有 **54 条短记录**。
  3. 对可疑记录用**当前管线**（`reorder_leads→filter_bandpass→resample_to_500→segment_to_5000→official_zscore`）重跑并与磁盘 npy 对比：
     - `cpsc_2018/A0798`（raw 4500 样本）→ 当前管线 500 零列，磁盘 500 零列，**identical=True**（已正确修复）。
     - `cpsc_2018/A1872`（raw 4500 样本）→ 当前管线 500 零列，磁盘 0 零列、max abs diff=0.1186（**未修复**）。
     - `cpsc_2018/A0240`（raw 4999 样本）→ 当前管线 1 零列，磁盘 0 零列、max abs diff=0.0165（**未修复**）。
  4. 原始 `.hea` 头确认样本数：A1872/A2695/A4229=4500、Q0561=4998、A0240/A0626/A4085/A5524/Q0045=4999。
- **受影响记录（9 条，实测）**：
  - 恒定非零填充（旧 z-score bug，`official_zscore` docstring 所述「零填充区变成非零常量 ~-mean/std」）：`cpsc_2018/A1872`、`A2695`、`A4229`（4500 样本）、`cpsc_2018_extra/Q0561`（4998 样本）。
  - 缺 1 样本零填充（4999→5000 应补 1 个零列，磁盘无）：`cpsc_2018/A0240`、`A0626`、`A4085`、`A5524`、`cpsc_2018_extra/Q0045`。
  - 划分分布：8 条在 train、1 条（A5524）在 val，test 无。
- **影响**：这 9 条记录的信号与其特征缓存（由 `extract_ecgfounder_features.py` 从旧 npy 提取）仍是旧管线产物，与当前「官方协议 + 零填充 z-score」口径不一致；3B-DP-T2 的修复只覆盖了 45/54 条。
- **修法**：补全 `SHORT` 列表（以 `duration_original < 10s` 的 54 条为准，而非硬编码 45 条），重跑信号重建 + 特征缓存按 id 替换；更稳妥是改为**按 manifest 动态探测短记录**（`duration_original < 10` 或重算 pad_left/pad_right），避免硬编码漂移。修后必须重跑 `verify_processed_5k.py` 并补充内容级校验（见 🟡-1）。

### 🟡-1 verify_processed_5k.py 只校验形状、不校验信号内容（零填充正确性），漏报 9 条 stale 记录

- **位置**：`scripts/verify_processed_5k.py` 第 54–66 行（形状检查）与第 108–116 行（健康度抽查）。
- **证据（实测）**：脚本对 `🟠-1` 的 9 条记录判「全部通过 OK」——第 58 行只检查 `x.shape != (12, 5000)`，这 9 条形状正确故不触发；第 55 行 `random.sample(data, min(60, len(data)))` 每划分仅抽 60 条做形状检查，第 110 行每数据源仅抽 1 条做 mean/std/nan 健康度检查（cpsc_2018 抽到的是全时长 A0001，非短记录）。
- **影响**：项目自身的「数据完整性闸门」无法发现信号内容级漂移（零填充、常量填充、z-score 口径），形成误判「数据健康」。
- **修法**：在第 2 节增加短记录内容校验：对 `duration_original < 10` 的记录断言「首/尾填充区应全零」且「非填充区 std≈1、无全零列」，或直接抽重跑管线对比；同时把形状抽样改为全量（37749 条逐个 `np.load` 约 9GB，可后台跑）。

### 🟡-2 fix_short_records.py「49 条」、preprocess_data_5k.py「48 条」与实列表 45 条三处数字不一致

- **位置**：`scripts/fix_short_records.py` 第 2 行 docstring「49 条短记录」vs 第 33–58 行实列表（45 条）；`scripts/preprocess_data_5k.py` 第 162 行注释「实测 48 条短记录受影响」。

- **影响**：文档误导后续维护者，且掩盖了「列表不完整」这一真实问题（见 🟠-1）。
- **修法**：统一为「54 条短记录（duration<10s），其中已修复 45、待补 9」；docstring 与列表/注释同步更正。

### 🟡-4 patch_incart_features.py 备份非幂等（无条件覆盖 .bak）

### 🟡-5 relabel_official_27.py 缺「manifest 行序 == 特征缓存行序」对齐断言（潜伏）

- **位置**：`scripts/relabel_official_27.py` 第 43–49 行（`kept` 按 manifest 顺序）vs 第 69–77 行（`sel` 按特征缓存 ids 顺序）。

- **影响**：若在 manifest 与特征缓存行序不一致的状态下重跑，会静默产出「manifest 行 ↔ 特征行错位」的缓存，下游逐行对齐被破坏且 evalset 校验查不出。
- **修法**：在第 77 行写 ids 前增加 `assert [ids[i] for i in sel] == [f"{m['source']}_{m['record_id']}" for m in kept]`（顺序断言）。

### 💡-1 leads_matched 大小写敏感、与 reorder_leads 大小写不敏感语义不一致

- **位置**：`scripts/preprocess_data_5k.py` 第 338 行 `leads_ok = (list(sample.lead_names or []) == STANDARD_LEADS)`（大小写敏感）vs 第 184–185 行 `reorder_leads` 用 `.upper()`（大小写不敏感）。
- **证据**：`.hea` 导联名大小写非标准（如全小写/全大写）时，`reorder_leads` 能成功重排到标准序，但 `leads_matched=False`，与代码注释「False 即匹配失败保持原序」语义冲突（实际还可能是「已重排」）。该字段仅存在于 preprocess 直接产出、权威 manifest 由 `patient_level_split.py` 从 `.bak_old27` 重写（实测 manifest 中 0 条含 lead_names 字段），影响面小。
- **修法**：`leads_matched` 改用 `[n.upper() for n in (sample.lead_names or [])] == [n.upper() for n in STANDARD_LEADS]`，或拆分为 `leads_reordered` / `leads_unmatched` 两字段。

### 💡-2 get_record_count 不跳过隐藏 .hea，主循环跳过 → tqdm 进度高估

### 💡-3 extract 脚本 --max-records 冒烟会覆盖生产缓存（无独立输出/无守卫）

- **位置**：`scripts/extract_ecgfounder_features.py` 第 50、118–121 行；`scripts/extract_text_embeddings.py` 第 54–55、78 行。
- **证据**：`--max-records N` 直接截断后写入默认生产 `output-dir`，会以 N 行覆盖全量 features/embeddings npy（下游 verify 会因行数不等而 FAIL，属于事后兜底，但缓存已损）。
- **修法**：冒烟模式强制重定向到临时目录，或 `--max-records` 时拒绝覆盖已存在的全量缓存（除非显式 `--force`）。

### 💡-4 extract_ecgfounder_features.py 缺文件静默跳过、产出与 manifest 错位

- **位置**：`scripts/extract_ecgfounder_features.py` 第 78–80 行 `logger.warning(...); continue`。
- **证据**：缺失 npy 时跳过该记录，产出 ids 长度 < manifest 行数，缓存与 manifest 错位；仅靠下游 `verify_processed_5k.py` 事后发现。

### 💡-5 --skip-existing 续跑无版本/一致性校验，会静默保留陈旧文件

### 💡-6 「ptb」源（97 条）按记录归患者，潜在患者级泄漏未被分组（数据限制）

- **位置**：`scripts/patient_split_prep.py` 第 25–32 行（仅 ptb-xl 走官方 patient_id，其余按记录）。

## 阳性结论

1. **权威数据整体健康**：`verify_processed_5k.py` 实测通过（exit 0）——npy 总数 37749、manifest 30232/3763/3754、特征缓存三件套与 manifest 逐行对齐（ids 行序 == manifest 行序）、患者级泄漏 train∩test/train∩val/val∩test 全为 0、37749 条 labels 与 LabelExtractor 在线编码 0 不一致、抽样信号 mean≈0/std≈1/nan=0。
2. **划分漂移防护健全**：`patient_level_split.py` 固定权威输入序（`.bak_old27`）+ `random.Random(42)` 确定性 shuffle + 双重锚点断言（`len(records)==37749`、`sizes=={30232,3763,3754}`），重跑幂等且防静默漂移。
3. **行序对齐防护到位**：`restore_authoritative_split.py` 第 62–66 行显式断言「manifest 行序 == ids 行序 == features/labels 行数」，杜绝 manifest↔特征错位。
4. **标签编码一致性**：`LabelExtractor` 27 类按 SNOMED 码字典序确定、`encode()` 默认 multi_hot，`preprocess_data_5k.py`/`patient_level_split.py` 均在线重编码（不复制旧 labels），实测 0 不一致。
5. **备份幂等模式已普及（多数脚本）**：`relabel_official_27.py`、`reprocess_incart_5k.py`、`fix_ptbxl_mojibake.py` 均以 `if not bak.exists()` 守卫备份，避免二次重跑覆盖原始备份（唯 `patch_incart_features.py` 例外，见 🟡-4）。
6. **resample_to_500 修复正确**：改用 gcd 约分后的真实比率 `resample_poly`（删除了历史「防爆内存」钳制循环）；INCART 257Hz 实测 `resampled_len=900000`、`new_tail100_zeros=0`，无时间压缩/尾部补零。
7. **fix_short_records.py 已修复的 45 条确属正确**：抽样 `A0798` 用当前管线重跑 identical=True，45 条零填充记录与列表一一对应。
8. **报告重建口径正确**：`rebuild_ptbxl_reports.py` 仅输出 manifest 实际使用的 ptb-xl 记录（21566 条）、优先回填患者级 split、对 38 条 CSV 空洞显式跳过并（代码层）落盘缺失清单，防「整份 CSV 全量写入」与「丢弃 split」两类历史问题。
9. **失败显式化已铺开**：`ECGLoader.failure_summary()` 汇总加载失败原因、`reprocess_incart_5k.py` 汇总 missing/n_done、`rebuild_ptbxl_reports.py` 落盘缺失清单、`reorder_leads` 匹配失败显式告警。
10. **废弃脚本标记清晰**：`preprocess_data.py`、`repair_manifest_5k.py`、`reprocess_e09680.py`、`restore_e09680.py` 顶部均标 `⚠️ DEPRECATED` 并说明保留原因，避免误用于现役流程。
