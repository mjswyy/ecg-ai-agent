## 🔴 确认缺陷（影响评估结论/训练目标）

### 🔴-1. `ECGTrainer.evaluate()` 在"被评估集合本身"上逐类定最优阈值 → 测试集 F1 / Challenge Score 系统性高估 ✅

- **位置**：`src/ecg_models/trainer.py:442-458`（阈值搜索在 446-452 行），影响所有把 test loader 传入 evaluate 的脚本：`scripts/train_backbone.py:194`、`scripts/train_simclr.py:175`、`scripts/train_ecgfounder_ft.py:133`、`scripts/eval_model.py:47`
- **问题**：`trainer.evaluate(loader)` 无论传入的是 val 还是 test，都在该集合上对每个类别做 `precision_recall_curve` + `argmax(F1)` 选阈值（446-450 行），再用这些"该集合最优"的阈值计算 macro_f1（457 行）与 Challenge Score（463 行）。AUC/mAP 是阈值无关指标不受影响，但 F1/Challenge Score 是"在测试集上作弊调阈值"的结果，系统性高估模型真实可部署性能。
- **证据（实测）**：用 `outputs/ecgfounder_mlp/mlp_head.pt` + 提取特征复算——验证集定 Youden 阈值 → 测试集 macro F1 = **0.3786**（与 metrics.json 一致）；测试集自身定阈值 → **0.4048**，膨胀 **+6.9%**。PR-F1 阈值口径方向相同。
- **对比**：`train_ecgfounder_head.py:70-81,230` 正确地在 val 上定阈值、在 test 上评估（其 0.9192 等数字我完整复现一致，见 🔴-1 的验证与"验证记录"章节）。
- **修法**：evaluate 增加 `thresholds` 参数（外部传入 val 定好的阈值）；或把"定阈值"与"评指标"拆成两个阶段，测试集评估必须用 val 阈值。

### 🔴-2. `eval_comprehensive.py` 在测试集上现算 Youden 阈值评 F1 + bootstrap 无种子 → 历史成绩单 F1 高估且 CI 不可复现 ✅（部分）

- **位置**：`scripts/eval_comprehensive.py:166-169`（阈值 166 行、F1 169 行）
- **问题**：该脚本（成绩单 0.791/0.808/0.822 与 `outputs/comprehensive_eval.json` 的来源）对每个模型在 **测试集** 上 `youden_thresholds(labels_test, probs)`（166 行）后计算 macro_f1（169 行）。与 🔴-1 同款泄漏：F1（如 xResNet 的 0.2413）是测试集调参后的乐观值。
- **证据**：代码路径明确（166 行阈值、169 行消费）；膨胀量级由 🔴-1 的实测（+6.9%）佐证。另见 🟠-4（同一文件 bootstrap 无种子）。
- **修法**：阈值必须来自 val 集（该仓库 `train_ecgfounder_head.py` 与 `src/evaluation/metrics/classification.py` 已是正确范式），脚本应传入 val 阈值。

### 🔴-3. `eval_ensemble.py` 在测试集上逐类 argmax-F1 定阈值评 macro_f1 ✅（代码级）

- **位置**：`scripts/eval_ensemble.py:90-95`
- **问题**：与 🔴-1 完全相同的问题：`precision_recall_curve(labels, probs)`（90 行）→ `argmax(f1_curve)`（92 行）→ 用该测试集最优阈值预测并评 F1（94-95 行）。集成的 macro_f1 高估。
- **证据**：代码路径明确；量级由 🔴-1 实测佐证。
- **修法**：与 🔴-1 相同——阈值必须在 val 上确定。

## 🟠 潜在缺陷（特定输入/边界触发）

### 🟠-1. `--patience 0`（文档称"禁用早停"）实际只训练 1 个 epoch ✅（实测）

- **位置**：`src/ecg_models/trainer.py:381-383`；参数声明 `scripts/train_backbone.py:80-81`（help="Early stopping patience (0 = disable)"）
- **问题**：`if patience_counter >= early_stopping_patience: break`。patience=0 时，第 1 个 epoch 后 `patience_counter`（无论是否改善均为 0）`>= 0` 恒成立 → 立即 break，训练恰好 1 个 epoch。文档承诺"0=禁用"与实际行为完全相反。
- **证据（实测）**：`train_multilabel(epochs=5, early_stopping_patience=0)` → `history["train_loss"]` 只有 1 条（仅跑了 1 epoch）。
- **修法**：`if early_stopping_patience > 0 and patience_counter >= early_stopping_patience: break`；或把 0 语义改为不 break。

### 🟠-2. 早停保存 best_model.pt，但训练返回/测试评估用的是"最后 epoch"权重 → 报告的测试指标与磁盘检查点不一致 ✅（实测）

- **位置**：`src/ecg_models/trainer.py:371-377`（只在 val 改善时 `_save_checkpoint("best_model.pt")`，从不把 best 权重回填模型）；训练后脚本直接 `trainer.evaluate(test_loader)`：`scripts/train_backbone.py:194`、`scripts/train_simclr.py:175`、`scripts/train_ecgfounder_ft.py:133`
- **问题**：早停触发时，函数返回的模型是最后 epoch 的权重（可能已过拟合），而 `best_model.pt` 是 best-val 权重。报告的 test 指标来自前者，生产/回放加载的是后者——两者不是同一个模型，数字与产物脱节。
- **证据（实测）**：构造 val_auc 递减序列（epoch1=0.9、之后 0.5，patience=1）→ 训练在 epoch2 早停；`model.state_dict()` 与 `best_model.pt` 的 `model_state_dict` 逐参数比较结果为 **False**（不一致）。而 `train_ecgfounder_head.py:186` 显式 `model.load_state_dict(best_state)` 再评估——正确范式，两脚本口径不一致。
- **修法**：train_multilabel 返回前 `self.model.load_state_dict(best_state)`（或返回 best_state 由调用方加载）。

### 🟠-3. `ECGAnomalyDetector.fit_threshold()` device 处理不一致：默认 device=None 时数据不搬到模型设备 ◻（代码级）

- **位置**：`src/ecg_models/classifiers/anomaly_detector.py:124-132`
- **问题**：循环内 `if device: x = x.to(device)`（126 行）——`device=None`（默认值，类 docstring 示例 `fit_threshold(normal_loader)` 即不带 device）时 x 留在 CPU；而 `anomaly_score()` 内部 `self.backbone(x)` 要求 x 与模型同设备。模型在 CUDA/NPU 上时直接崩（RuntimeError: Expected all tensors to be on the same device）。同时阈值张量却按模型设备创建（129-132 行），说明作者已意识到 device 问题但只修了一半。
- **证据**：代码路径明确；本机无 CUDA 无法实跑，标 ◇。
- **修法**：统一用 `next(self.parameters()).device` 搬运 x（127 行已有该表达式可用于 dev，直接复用）。

### 🟠-4. `eval_comprehensive.py` bootstrap CI 用全局 `np.random` 且无种子 → CI 不可复现 ◻（代码级）

- **位置**：`scripts/eval_comprehensive.py:31-40`（35 行 `np.random.choice`）
- **问题**：`bootstrap_auc_ci` 未设置任何种子，每次运行 CI 不同；且与 `train_ecgfounder_head.py:42-67` / `src/evaluation/metrics/classification.py:13-45` 的 `RandomState(seed=42)` 口径不一致。`outputs/comprehensive_eval.json` 中的 CI（如 xResNet [0.7737, 0.8061]）无法复现。
- **证据**：代码级确认；未重复运行验证（避免耗时>5min）。
- **修法**：改 `rng = np.random.RandomState(42)` 并统一口径。

### 🟠-5. 10 处 `weights_only=False`（范围内 7 处）：任意检查点文件 → 任意代码执行风险；且与 torch≥2.6 新默认冲突 ✅（已验证必要性，但模式危险）

- **位置**：`scripts/extract_ecgfounder_features.py:38`、`scripts/train_ecgfounder_ft.py:40`、`scripts/eval_comprehensive.py:24`、`scripts/eval_topk.py:22`、`scripts/eval_ecgfounder.py:31`、`scripts/eval_agent.py:35`、`scripts/analyze_ecg.py:31`（范围内 7 处；另 `src/agent/tools/ecgfounder_classifier.py:51,63`、`scripts/train_multimodal.py:52`、`scripts/train_multimodal_fair.py:173` 范围外）
- **问题**：`weights_only=False` 会 pickle 反序列化任意对象；`eval_comprehensive.py`/`eval_topk.py` 的 `--checkpoint` 参数接受外部路径，恶意检查点可执行任意代码。torch 2.6+ 默认已改为 `weights_only=True`，显式关掉属于倒退。
- **证据（实测）**：ECGFounder 官方 ckpt 含 `numpy.core.multiarray.scalar`（`val_auroc = np.float64(...)`，实测确认），`weights_only=True` 加载确实抛 `UnpicklingError: Unsupported global`——**对该官方文件，weights_only=False 是当前必需的**。正确做法是 `torch.serialization.add_safe_globals([np.float64, np.int64, ...])` 后保持 weights_only=True，而非全局关闭。
- **修法**：对官方 ckpt 用 `add_safe_globals` 白名单；对用户可指定的路径（eval_* 脚本）保持默认 weights_only=True 并校验来源。

### 🟠-6. `QTAnalyzer.analyze()` 只捕获 ImportError：neurokit2 已装但 `ecg_delineate` 抛 ValueError/TypeError 时异常穿透崩溃 ◻（代码级）

- **位置**：`src/ecg_models/feature_extraction/qt_analyzer.py:85-89`（对比 `r_peak_detector.py:76-78` 捕获 `(ImportError, ValueError, KeyError)`）
- **问题**：neurokit2 安装但信号过短/波形质量差时，`nk.ecg_delineate` 常见抛 ValueError/TypeError（该库对短信号、无 QRS 的输入并不总是安全返回 NaN）。此处只捕 ImportError → 异常穿透 `analyze()` → `FeatureBank.extract_all()`（`feature_bank.py:94-96`）→ 上层 agent/分析脚本整体崩溃，而不是按文档回退到 `_simple_delineate`。
- **证据**：代码级确认（捕获列表与兄弟模块不一致，文档承诺"如不可用则回退"但实现只覆盖未安装场景）。
- **修法**：捕获 `(ImportError, ValueError, TypeError, KeyError)` 并回退。

### 🟠-7. `analyze_ecg.py` 对 150 类 logits 一律 `sigmoid`，假设 ECGFounder 分类头是 BCE 多标签训练 ◇（疑似，无法从 ckpt 证实）

- **位置**：`scripts/analyze_ecg.py:53-55`
- **问题**：ECGFounder 官方 ckpt（`12_lead_ECGFounder.pth`）不携带训练目标配置（实测 ckpt 顶层仅 `epoch/step/state_dict/optimizer/scheduler/val_auroc`）。若其 150 类头是 softmax-CE 训练（PTB-XL 单标签 benchmark 的常见设定），则逐类 sigmoid 得到的"概率"无 softmax 分母，数值被系统性抬高、0.3/0.7 的等级阈值与 top-k 排序都会失真。`val_auroc` 字段暗示其用 AUC（倾向 BCE），但不足以证实。
- **证据**：ckpt 结构实测；训练目标无法从权重推断（◇）。
- **修法**：查 ECGFounder 官方训练配置确认损失；若为 softmax 则改为 softmax 输出并按 argmax 排序。

## 🟡 可维护性 / 风格

### 🟡-1. `_save_checkpoint` 保存的 `best_metric` 恒为 0.0 ✅（实测）
- `src/ecg_models/trainer.py:574-577`：保存的是 `self.best_metric`，而该字段只在训练循环**结束后**（386 行）才被赋值为 `best_val_auc`——训练期间保存的所有检查点 `best_metric` 都是初值 0.0。
- **证据（实测）**：4 个 `checkpoints/*/best_model.pt` 的 `best_metric` 全部为 0.0（epoch 29/35/37/39）。
- **修法**：保存时写 `best_val_auc`（或维护独立的 `self.best_val_auc` 字段）。

### 🟡-2. `torch.cuda.amp` 已弃用，torch 2.7 每个 step 输出 FutureWarning ✅（实测）

### 🟡-3. `train_ecgfounder_ft.py` 全程无随机种子 → 不可复现 ◻（代码级）

## 💡 建议

### 💡-1. 标签平滑公式 0→0.5ε（非标准 ε），与 ASL 混用时未文档化
- `src/ecg_models/trainer.py:299`：`labels * (1-ε) + 0.5*ε`（0→0.05，1→0.95，ε=0.1）；`train_ecgfounder_head.py:162` 用同式（`yb*0.9+0.05`），两处一致。但 `train_backbone.py:174-177` 把 `AsymmetricLoss` 与标签平滑叠加时，soft target 会让 ASL 的 `targets`/`(1-targets)` 掩码变成软权重，聚焦语义（γ_neg=4）被稀释——建议文档化或在 ASL 路径禁用平滑。

### 💡-2. AMP 后端选择策略：NPU 优先于 CUDA
- `src/utils/device_utils.py:121-131`：只要 `import torch_npu` 成功就选 NPU AMP，即使当前实际跑 CUDA。若某环境同时装了 torch_npu 与 GPU，会选错后端。建议按 `detect_device()` 的结果选择。

### 💡-3. bootstrap CI 的类别漂移
- `scripts/train_ecgfounder_head.py:54-66`（及 canonical 同款）：重采样行后，某类可能整类掉出，宏平均的类别数逐次变化 → CI 略偏窄。建议固定类别集合（用全量数据判定可用类，重采样中该类不可算时跳过整个 resample 或记 0.5）。

### 💡-4. `_cosine_schedule` 边界：warmup ≥ epochs
- `src/ecg_models/trainer.py:552-566`：`T_max=max(epochs-warmup, 1)`，若 `warmup>=epochs`，余弦阶段只有 1 epoch 后 LR≈0，训练近乎停摆。建议校验参数或对 warmup 封顶。

### 💡-5. `FeatureBank.to_vector` 缺失特征静默填 0
- `src/ecg_models/feature_extraction/feature_bank.py:130-139`：缺失 key 填 0.0（有 warning 但调用方通常不打印）。下游模型会把"缺失"当作真实 0 值。建议返回 mask 或允许显式失败。
