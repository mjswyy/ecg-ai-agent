## 🔴 严重问题（影响评测结论 / 伪指标 / 泄漏）

### R1. 「报告辅助」对照臂存在地面真值泄漏，该臂判官正确性分不可作为"报告辅助有效"的证据 【确认】

- **位置**：`scripts/eval_agent_llm.py:304`；`scripts/build_agent_evalset.py:139-156`
- **描述**：报告辅助臂把医生原始报告 `item['report_text']` 直接注入报告生成提示（"医生原始报告: ..."）。而该报告的诊断内容与评估用地面真值 `dx_names` 同源（PhysioNet 2020 的 ptb-xl 报告/SCP 码是对同一份心电图临床解读的两种形式），随后判官又拿报告与同一份 GT 标签比对打分（`rubric_judge.py:30` "真实标签(ground truth): {gt}"）。模型只需转述医生报告即可在 correctness 维度得高分——该臂的正确性提升是泄漏上界，不是"报告辅助"的因果效果。
- **证据（实测）**：抽查 evalset 中带 report_text 的记录：
  - `HR10752`：dx=`['Atrial Flutter','Left Bundle Branch Block','Myocardial Infarction','Myocardial Ischemia']`，报告原文 "rhythm is atrial flutter with 2:1 av block..." → 直接陈述 GT 诊断；
  - `HR01126`：dx 含 Atrial Fibrillation，报告 "atrial fibrillation with slow ventricular response..."；
  - `HR01232`：dx 含 Sinus Bradycardia / PAC / First Degree AV Block，报告 "sinus bradycardia. premature atrial contraction(s)... prolonged pr interval 0.24 sec"。
  - 产物 `outputs/agent_eval/judge_rubric_results.json`：report_arm correctness mean=2.579 vs main=2.436，差异被此泄漏污染。
- **修法**：报告辅助臂的对照结论必须改为"仅对无医生报告样本评估"或把医生报告按诊断子集打码后再注入；判官打分时对 report_arm 标注"复制人类报告"惩罚项；论文中该臂结论应降级为"提示词工程对照"而非临床增益。

### R2. `findings_gt_overlap` 分母定义错误，产物中"重合率"=1.5484（>1），是定义上不可能的伪指标 【确认】

- **位置**：`scripts/eval_agent_context.py:246-248`（分子）、`:248`（分母）、`:273`（输出）
- **描述**：分子按**每个情境**累加 `len(s & gt)`（同一记录 3 个情境各加一次），分母 `gt_total += len(gt)` 却在情境循环**外**每记录只加一次。结果比率 = Σ_记录 Σ_情境|findings∩gt| / Σ_记录|gt|，可任意 >1（gt 只有 1 个标签、3 个情境都列出该标签时单记录贡献 3/1）。"重合率"把情境冗余当成覆盖度。
- **证据（实测重算）**：
  ```
  aggregate(records.jsonl)（当前代码）→ findings_gt_overlap = 1.5484 （与磁盘 metrics.json 一致）
  按"记录×情境"口径重算 → Σ|s∩gt| / Σ|gt| = 144/279 = 0.5161
  ```
  即产物中的 1.5484 是正确口径 0.5161 的 3 倍，直接进论文会被引为"发现层重合率 155%"。
- **修法**：`gt_total += len(gt)` 移入 `for s in nonempty:` 循环内（按情境-记录对归一），或在注释与命名中明确"每记录最多 3 次贡献"的口径并改名为 coverage×contexts。

### R3. 三臂跨臂不可比：注入只作用于主分支，report/kb 臂在干净输入上评测，判官/幻觉/工具指标的跨臂对比被混淆 【确认】

- **位置**：`scripts/eval_agent_llm.py:206-225`（`if (not self.use_report and not self.use_kb and self.rng.rand() < ...)`）；产物 `outputs/agent_eval/metrics_report_arm.json`、`metrics_kb_arm.json`（`n_injected: 0`）
- **描述**：主分支 7.5% 记录的工具 top-1 被篡改为与实测心率矛盾的高置信诊断；report/kb 臂**完全没有注入**，其输入是干净的。于是：
  1. 三臂的 LLM-as-judge 正确性/幻觉率是在**不同难度的输入**上测的（主分支更难），report_arm 的 correctness 优势（2.579 vs 2.436）除 R1 泄漏外还叠加了任务难度差异；
  2. 注入纠错指标在 report/kb 臂恒为 None（`n_injected=0`），三臂在该维度上无对比基础；
  3. 幻觉率 main 0.0033 vs report 0.0051 / kb 0.0052 的"反直觉"差异正是输入不对称的体现。
- **证据**：`metrics_report_arm.json` / `metrics_kb_arm.json` 的 `injection.n_injected=0`、`catch_rate_report=null`；`metrics_main.json` 的 `n_injected=10`。
- **修法**：注入改为三臂同策略（或按臂报告"有注入/无注入"分层指标）；跨臂对比只允许在"输入难度相同"的前提下进行，论文须明示该不对称。

## 🟠 潜在缺陷

### O1. 注入有效比例 7.5%（10/133）远低于声称的 20%，100% 捕获率基于 n=10 【确认】

- **位置**：`scripts/eval_agent_llm.py:13`（docstring "注入 20%"）、`:200`（注释 "注入可检测矛盾（20% 记录，仅主分支）"）、`:207`（`self.rng.rand() < self.inject_error_frac`）、`:214-225`（HR<60 或 ≥100 才注入）
- **描述**：`inject_error_frac=0.2` 只是 rand() 门限；实际注入还要求实测心率 <60 或 ≥100 且 top1 不是同义诊断，多数记录（60-100 bpm）永不注入。产物 `metrics_main.json`：`n_injected=10`（7.5%）。`catch_rate_report=1.0`（10/10）与 `catch_rate_verdict=1.0` 的小样本脆弱性极高：任一漏报即跌到 90%/80%。
- **证据**：`outputs/agent_eval/_recompute_v3_report.txt` 与 `records_main.jsonl` 均只有 10 条 injected；`injection_desc` 全部为 "实测心率≥100 却报窦缓" 类。
- **修法**：注入条件放宽（如按 HR 与 top1 语义矛盾构造任意心率下的矛盾对）或把"实际注入率"写进指标与论文；报告 catch rate 同时给出 n 与 95% CI（n=10 时无意义）。

### O2. 缓存 key 的温度分量与实际采样温度不符（key 写 t=0.0，真实请求恒为 0.3）【确认】

- **位置**：`scripts/eval_agent_llm.py:130-145`（`ask()` 的 `temperature=0.0` 只进缓存 key，从不传给 `llm.chat`）；`src/agent/llm/llm_interface.py:86`（默认 `temperature=0.3`）、`:172-177`（`chat()` 恒发送 `self.temperature`）；`scripts/eval_agent_context.py:70-103`（`ContextCache` key 写死 `t=0.0`，`ask()` 同样不传温度）
- **描述**：所有实际请求以 0.3 采样，但缓存 key 全部宣称 `t=0.0`。docstring（eval_agent_llm.py:18）声称 "temperature=0.3 … 全链路同温" 与实现相悖。后果：① 复现性声明失真；② 若未来把 LLMInterface 默认温度改为 0.7 或构造时传不同温度，旧缓存（key 仍 t=0.0）会静默返回旧温度下的响应，跨配置污染。
- **证据**：`ask()` 中 `kwargs` 仅含 `response_format`（:140-143），temperature 参数无任何下游使用；`llm_cache.jsonl` 中 1770 条 key 均为 64 位哈希，无法与真实请求参数对应。
- **修法**：`ask()` 把 temperature 透传给 `llm.chat`（或移除该参数并让 key 直接编码 `self.llm.temperature`），ContextCache 同理；key 中同时加入 `max_tokens`。

### O3. Rubric 判官缓存 key 缺模型名/温度，跨模型重打分会命中旧模型缓存 【确认】

- **位置**：`src/agent/llm/rubric_judge.py:43-46`（`_key = sha256(gt|report[:1500])[:20]`）；`scripts/rejudge_with_rubric.py:38`（`--model` 可改）、`:47`（共享 `judge_rubric_cache.jsonl`）
- **描述**：`RubricCache` 的 key 只含 gt+截断报告，不含模型名/温度/json_mode——与主评测 `ResponseCache._key`（eval_agent_llm.py:71-74，含 model/json/temperature）不一致。若先后用 `--model deepseek-chat` 与 `--model deepseek-reasoner` 重打分，或模型服务端升级，缓存直接返回旧模型评分。
- **证据**：`judge_rubric_cache.jsonl` 790 条 key 全部为 20 字符；同一判官请求在主缓存（64 位，含模型）与判官缓存（20 位，无模型）中 key 不同（实测 `14c567c6...` vs `90108d80...`）。
- **修法**：`RubricJudge` 构造时接收 model 名并入 key；或复用主 `ResponseCache` 的口径。

### O4. 判官解析失败的处理两套不一致：评测 harness 内失败→全 1 分（伪装成"质量极差"），rejudge 路径失败→None 跳过 【确认】

- **位置**：`scripts/eval_agent_llm.py:386-392`（`except ...: s = {"correctness": 1, ...}`）；`src/agent/llm/rubric_judge.py:67-71`（"判官故障返回 None 由调用方跳过并单独统计，旧版全给 1 分会把'LLM 故障'伪装成'报告质量极差'"）
- **描述**：rubric_judge.py 明确否定的"失败给 1 分"做法，在 eval_agent_llm.py 的内联判官路径原样存在：LLM 输出 JSON 解析失败即记 1/1/1/1 并计入均值，把模型故障系统性下拉分数。rejudge 路径则跳过并计 `judge_failures`。同一批报告两套管线会得出不同均值。
- **证据**：代码对比；`judge_rubric_results.json` 中 kb_arm 含 `judge_failures: 0` 而 main/report_arm 无该键（文件混版本，见 Y4），说明两套逻辑都实际运行过。
- **修法**：统一为"失败→None→`judge_failures` 单列"，harness 内联路径直接调用 `RubricJudge.score()`（顺带消除死代码，见 Y8）。

### O5. `recompute_agent_metrics.py` 无条件以 `judge_scores=None` 覆写 `metrics_main.json`，若原跑带 `--judge` 则判官分数被静默删除 【确认】

- **位置**：`scripts/recompute_agent_metrics.py:41-46`（`aggregate_metrics(ok, judge_scores=None, ...)` 后直接 `json.dump` 覆盖）
- **描述**：重算脚本为修复注入污染重跑 aggregate，但硬编码 `judge_scores=None`，把原 `metrics_main.json` 中可能存在的 judge 结果抹掉。当前磁盘产物 `metrics_main.json` 的 `"judge": null` 无法区分"原跑未开 --judge"还是"被重算抹掉"。
- **证据**：`_recompute_v3_report.txt` 中 old metrics 也是 `"judge": null`（此例原跑未开 judge），但脚本逻辑上存在该数据丢失路径。
- **修法**：重算时从旧 metrics 读取并透传 judge_scores（若存在）；或禁止重算覆写 judge 字段。

### O6. 幻觉率分子/分母口径不一致：工具值缺失时的数值声明进分母不进分子，比率被系统性低估 【疑似】

- **位置**：`scripts/eval_agent_llm.py:340-341`（`if tool_val is None: continue`，工具失败则跳过检查）；`:464-471`（aggregate 用正则数全部声明进 `n_claims`，不区分工具是否可用）
- **描述**：某条记录 QTc 工具失败（qtc=None），报告若写 "QTc 450"：eval_one 不标记幻觉，但 aggregate 的 `n_claims` 会把这句计入分母 → 分母 > 可被判定为幻觉的声明数，比率被低估；同时"工具缺失却编造数值"本应是更强的幻觉信号却被漏掉。
- **证据**：代码路径确认；`metrics_main.json` n_claims=611 可完全由正则重算复现（实测一致）。实际影响：对 15 条 evalset 记录重跑确定性工具，rpeak/hrv/qt/classifier 失败率均为 0，故当前产物受影响有限（工具在该数据上稳定）。
- **修法**：把"工具值缺失但报告声明了对应数值"也计入幻觉分子（或至少从 n_claims 排除无对应工具值的声明）；记录级缓存 tools_out 以便复算。

### O7. `evaluate()` 缺省在评估集上现算 Youden 阈值，`macro_f1_youden` 属样本内拟合（乐观）【确认，设计自认】

- **证据**：代码路径；`outputs/ecgfounder_mlp/metrics.json` 的 thresholds 为验证集口径（与 `eval_per_class` 一致），而 `train_multimodal_fair.py:28` 调用 `evaluate()` 时未显式传 thresholds（该脚本不在本轮范围，但默认行为即本问题）。
- **修法**：`evaluate()` 去掉默认现算，改为要求显式传 thresholds 或统一从验证集加载。

### O8. `build_context_subset.py` 的 blocks 分层用缩写类名，与 LabelExtractor 全名永不匹配，分层失效（子集 36 条 ≠ 声明 40 条）【确认】
