## 发现清单

### 🔴-1 preprocess_data_5k.py 全量运行会在写 manifest 时崩溃：labels 为 np.ndarray 无法 json 序列化
- 位置：`scripts/preprocess_data_5k.py:376-383`（赋值）与 `:385-389`（json.dump）
- 证据：
  - 代码：`_encode_labels` 返回 `_le.encode(dx)`（label_extractor.py:121-149 确认默认 format="multi_hot" 返回 `np.zeros(27, dtype=np.float32)`，即 **np.ndarray**）；随后 `m["labels"] = _encode_labels(m)` 把 ndarray 直接塞进 manifest 条目，再 `json.dump({"files": files, ...})`。
  - 实测：`json.dump({"labels": np.zeros(27, dtype=np.float32)}, io.StringIO())` → `TypeError: Object of type ndarray is not JSON serializable`；`LabelExtractor(num_classes=27).encode(["426783006"])` 返回 `type=ndarray, dtype=float32, shape=(27,)`。
  - 对比：同目录其余所有写 labels 的脚本均显式 `.tolist()`（preprocess_data.py:131、relabel_official_27.py:48、patient_level_split.py:88），唯独本脚本第 4 步漏掉。
- 影响：本脚本 docstring 明确"重跑本脚本后必须重跑 patient_level_split.py 恢复患者级划分"，是主数据生成入口。全量运行会在最后一步 `json.dump` 抛 TypeError，npy 已写盘但 manifest 全部未写 → processed_5k 处于"有信号无 manifest"的损坏态。冒烟模式（--max-records）因提前 return 而不会触发，故该缺陷长期潜伏。
- 修法：`return _le.encode(dx).tolist() if dx else [0] * 27`（对 ndarray 加 `.tolist()`）。

### 🟠-2 restore_authoritative_split.py 对 manifest 排序、对特征缓存不排序 → 运行后 manifest 与特征行错位
- 位置：`scripts/restore_authoritative_split.py:21-26`（manifest 按 `(source, record_id)` 排序写回）vs `:40-46`（features/ids 按 `_authoritative_ids.json` 原始顺序组装）
- 证据：
  - 实测 `outputs/patient_level/_authoritative_ids.json`：`auth == sorted(auth, key=(source,record_id))` 为 **False**（train 前 5 条为 `cpsc_2018_A0015, A0016, A0018, A0020, A0027`，非从 A0001 开始的排序序）；而当前 manifest `mid == sorted(mid, key=(source,record_id))` 为 **True**。
  - 第 1 步 `files.sort(key=lambda r: (r["source"], r["record_id"]))` 使写出的 manifest 为排序序；第 2 步 `rows = [id_loc[eid] for eid in ids]`（ids 取 auth 原始未排序序）写出的 features/labels/ids 与 manifest 顺序不一致。
  - 本项目下游严格按"manifest 行 ↔ ids 行 ↔ features 行"逐行对齐（extract_ecgfounder_features.py:76-87 按 manifest 迭代顺序生成 ids；patient_level_split.py/relabel 均把特征重排到与 manifest 一致），因此顺序错位 = 特征与标签/记录错配。
  - 第 3/4 步的泄漏校验（仅患者集合重叠）与 evalset 校验（仅 test 成员资格）都**不会**发现该错位，运行后误报"✅ 全部确认"。
- 影响：恢复脚本一旦被实际执行，会静默破坏"特征↔标签↔记录"的行对齐，污染训练/评测数据。
- 修法：第 2 步对每个 split 先 `ids = sorted(ids, key=lambda eid: tuple(eid.split('_', 1)))` 再组装 features/labels，使特征序与第 1 步排序后的 manifest 序一致；或统一不排序。

### 💡-9 reorder_leads 匹配失败时静默保持原导联顺序，可能以错误导联序送入模型

## 阳性结论（实测验证正确的性质）

1. **权威划分规模与磁盘一致**：processed_5k manifest = 30232/3763/3754 = 37749；磁盘 npy 数 = 37749；三者 manifest 引用的 npy 全部存在（缺失 0）。
2. **特征缓存与 manifest 逐行对齐**：train/val/test 的 `{split}_ids.json` 长度 == `features.npy` 行数 == `labels.npy` 行数 == manifest 条数（30232/3763/3754），且 ids 顺序 == manifest 顺序（`ids == manifest order: True`）。
3. **manifest 标签 == 特征缓存标签**：三划分逐行比对 `manifest-label vs feature-label mismatch = 0`；labels dtype float32、shape (n,27)。
4. **患者级泄漏为 0**：`record_patient.json` 覆盖全部 37749 条（0 缺失），train∩test / train∩val / val∩test 患者重叠均为 0。
5. **信号形状健康**：三划分各抽前 500 条 shape 均为 (12,5000)，异常 0；`labels/snomed_to_class.json` num_classes=27、class_names 27 条与 relabel_report 一致。
6. **标签编码全链一致**：LabelExtractor.encode 默认 format="multi_hot" 返回 27 维 one-hot 向量，relabel_official_27.py:48、patient_level_split.py:88 均 `.tolist()` 后再写 JSON，与 preprocess_data.py:131 一致（唯一例外即 🔴-1）。
7. **划分漂移防护生效**：patient_level_split.py:53 断言 `len(records)==37749`、:79 断言 `30232/3763/3754`、:130 断言泄漏为 0；实测三者与磁盘状态吻合。
8. **relabel 内部计数自洽**：bak_old27 总量 43101（30167/6462/6472），relabel_report 记录 30167→26384、6462→5687、6472→5678（合计 kept=37749、dropped=5352），与权威总数一致；`features_rows_kept` 各等于 new_count。
9. **INCART 特征补丁非破坏性**：feature_patch_report.json 三划分 `non_incart_rows_unchanged: true`、`ids_unchanged: true`。
10. **报告 split 已同步**：ptbxl_reports.json 中所有条目 `split` 无 missing/unknown；对仍在 manifest 内的记录，report split 与 manifest split 不一致数 = 0；text_embeddings 的 report_splits 对在册记录亦 0 不一致。
11. **18 个脚本语法全部通过**（ast.parse 18/18 OK）。
